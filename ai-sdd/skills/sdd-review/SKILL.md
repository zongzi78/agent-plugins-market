# sdd-review（质量循环引擎）

## 定位

工件无关的**质量循环引擎**，不是新的流程阶段。定义循环（首轮 → 修复 → 回归 → 终审）与档位（中杯 / 大杯 / 超大杯）：「审」由独立 reviewer subagent 执行，「修」由主 agent 在循环内执行，终审由新眼睛放行（PASS 即终止）。

**不负责「审什么、按什么标准审」**——那由**调用方**通过 `criteria` 传入。本引擎不做工件之外的扫描、诊断或归并。

## 一、核心概念（四个词，全文只用这些）

| 词 | 含义 |
|---|---|
| **职责面** | 本次变更目标与验收标准（criteria）+ 被审工件与直接受影响区域（由 diff / 受影响区域清单界定）。用于判定一条问题算不算「必修」。 |
| **台账** | 带固定格式的问题记录，主 agent 维护；**每轮完整注入 reviewer（含 closed 项）**，不裁剪。 |
| **核销** | 在回归轮把台账中**上轮的 open 项判定为 `closed`**（即验证其修复成立）。核销时在台账上记下**核销人**（该 reviewer 的标识）。 |
| **新眼睛** | 一个**从未核销过**的 reviewer 上下文。终审必须由新眼睛执行——即「**核销者不得自证**」。 |

> **判据落在"上下文"，不是"轮次"。** 只要某个 reviewer 核销过哪怕一次，它**此后就丧失了终审资格**；反之，一个从未核销过的上下文可以审任意多轮、也可担任终审。
>
> 「新眼睛」是**资格**，不是进程形态——它**不要求**新开 subagent：只要该上下文从未核销过，续接它另起一轮同样合格。

## 二、角色与独立性（铁律）

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| **主 agent**（编排方） | 维护台账；核实并**修复**；产出修复 diff 与受影响区域；核定问题归属与处置 | **不得自任 reviewer，不得自审** |
| **reviewer**（独立 subagent） | 只审：按 criteria 输出 findings | **只审不改**；不产生修复动作 |
| **调用方** | 提供 `criteria` 与约束注入；消费「评审记录」 | 不介入循环内部 |

- **独立性 = 独立上下文 + 不是产出者。** 评审**必须**由独立上下文的 reviewer subagent 执行（按 `prompts/reviewer.md` 构造）；编排方不得用自己刚审阅过该工件的上下文「直接读一遍」代替评审。
- **不要求每轮更换 reviewer**——回归轮默认**续接**原 reviewer（见 §4.5）。
- 若环境无法派发 subagent：须先声明「独立性受限、评审不可信」，以受限方式继续并报告。此路径不代表评审具独立性，属**兜底降级**。

## 三、输入参数

| 参数 | 类型 | 说明 | 必填 |
|------|------|------|------|
| `artifact` | enum | `文档/计划类` \| `产物类`（代码/文档/配置等；独立调用时由目标推断） | 调用方调用时是 / 独立调用时可省略 |
| `criteria` | 引用/内联 | 评审检查清单**内容**（由调用方提供，非仅名称） | 同上 |
| `depth` | enum | `中杯`（默认）\| `大杯` \| `超大杯` | 否 |
| `max_rounds` | int | 评审轮总上限（全局计数，见 §5.3），默认 6 | 否 |
| `artifact_path` | path | 工件路径（文档/计划类工件，或产物文件列表） | 是 |
| `workdir` | path | 项目根目录 | 是 |
| `context` | 文本 | 调用方共享上下文（背景/约束/前一阶段信息）；引擎从中提取评审所需部分注入 reviewer，**不得把整段会话历史塞给 subagent** | 否 |
| `diff 基线` | 引用 | 首轮为「全量」；回归/终审轮提供修复 diff 与受影响区域清单 | 否 |

**调用方式**

- **作为闸门引擎**（被上游流程调用）：调用方进入本引擎（同一主 agent 会话），传入上述参数；引擎运行循环，产出「评审记录」（PASS / 未收敛）。
- **独立调用**（用户直接触发）：`/sdd-review <目标> [深度]`。目标可省略（默认最近一次被审工件），深度可省略（默认中杯）。目标类型无法判断时**向用户确认一次**，不反复追问。
- **独立调用默认标准**（无调用方提供 criteria 时兜底，仅通用维度）：目标回应（是否回应初始需求、有无越界新增）／结构（粒度可验证、依赖顺序合理）／覆盖（风险是否覆盖每个改动点）／红线（是否违反项目规则声明的权限边界与文档红线）／一致性（设计与产物现实是否匹配）。

## 四、循环算法（唯一入口）

```
循环 = 首轮 →（修复 → 回归）* → 终审
```
所有轮按**全局评审轮数**计数（首轮 / 回归 / 终审合计，见 §5.3）。

### 4.1 阶段 0：前置事实核查（仅限 AI-SDD 产出物）

> **适用范围**：仅对 AI-SDD 体系内的产出物生效；独立调用本 skill 或评审其他工件时**跳过**（如需可显式要求执行）。

1. 适用时运行 `scripts/checks` 直到**无 FAIL**——有 FAIL 则主 agent 先修机械项再重跑；**FAIL 期间不派 reviewer**。WARN 记录、不阻塞。
2. 通过后，其输出（事实清单）随 reviewer 输入一并随附。
3. 明确**职责面**（见 §1）。

checks 只做事实核查（编号与引用 / 文件与链接存在性 / 模板必需字段 / 占位符残留 / 勾选与状态一致性 / diff 范围 vs plan / 台账格式），**不做语义评审**。Windows 用 `scripts\checks.ps1`，Unix 用 `scripts/checks`。

### 4.2 阶段 1：首轮（全量）

1. **必须** dispatch 独立 reviewer subagent（按 `prompts/reviewer.md` 构造）。输入 = `artifact_path` + `criteria` + 约束注入 + 职责面 + 空台账。
2. 为该 reviewer 指定**本循环内的稳定标识**，并**记为它的上下文编号**（见 §4.5）。
3. 首轮**读足**：全量 + 局部深挖 + 必要的针对性验证——把成本花在减少后续补漏轮上。
4. 输出 findings-only（见 §5.1）。
5. 主 agent 并入台账并分类（见 §5.2）。

### 4.3 阶段 2：修复与回归（按需循环）

1. **修复**（主 agent 在循环内执行，不 dispatch 独立 fixer subagent）：
   - **逐条核实** reviewer 提出的问题是否确实成立（对照工件与 diff，**不凭声明**）；
   - 对**确实存在**的问题——属职责面内、或涉及安全 / 数据损坏 / 不可逆类——**必须修复**；只改本次相关工件，不越界；
   - 不成立的：驳回并写明理由（记入台账）；Minor 仅记录、不阻塞；
   - 全部修完后自验，产出「**修复 diff + 受影响区域清单**」。
2. **回归轮**：输入 = **完整台账 + 修复 diff + 受影响区域**；**续接原 reviewer**（见 §4.5）。
   - 编排方**不得以成本为由裁剪 reviewer 输入或限制其读取**；读取自主权见 `prompts/reviewer.md`。
   - 输出：上轮 open 项 → **closed / reopened**（若本轮把某条 open 判为 closed，**就在台账上记下"核销人 = 该 reviewer 标识"**）；修复引入的新问题；新发现（按三档分类）。
3. **退出条件**：台账中职责面内**无 open 的 Critical/Important**，且本轮**无新增**职责面内 Critical/Important。
4. 每轮结束检查总轮数是否达到 `max_rounds`（见 §6.2）。

### 4.4 阶段 3：终审（新眼睛放行）

**触发**：本循环发生过任何修复。全程未发生修复 → **无终审轮**（末轮本身就是新眼睛的独立评审）。

1. **选定终审者**：必须满足两条——① 该轮不做核销（只验证，不改台账状态）；② **其上下文从未核销过任何一轮**（见 §1「核销」）。两条缺一不可。
   > 判据落在**上下文**而非**轮次**：同一个 reviewer 即便某一轮没核销，只要它**此前核销过**，就已丧失终审资格。否则等于"我核销的、我再宣布整体通过"，自证未被阻断。
2. 终审输入 = 完整台账 + 修复 diff + 受影响区域；任务是**独立验证「修复到位 + 无回归」**——可抽查 / 定点读，**不做全量重审**（除非确有必要并说明理由）。
3. 终审 **PASS → 循环结束**。**PASS 即终审，不做多级确认**。
4. 终审提出新的职责面内 Critical/Important → 该 reviewer **转为工作轮 reviewer**（由它负责后续修复回归）；修完后须由**另一位**满足上述两条的 reviewer 放行，直到某位终审的 PASS。

> **禁止**把「开新 subagent」当作终审合规的证明；也**禁止**为了「更独立」而每轮开新 subagent——那是成本浪费，不是严谨。

### 4.5 reviewer 上下文与凭据

**默认：回归轮必须续接原 reviewer 上下文**（续接 = 把输入发回该标识，而非新建）。新建是**例外路径**。

本引擎不点名任何具体工具，判据只描述**能力**（能否向已结束的 subagent 再发消息 / 能否按其标识恢复其上下文）。

- **凭据存放（不新增产物）**：首轮 dispatch 时写明「本循环内以 `<标识>` 指认本 reviewer」，并把它**随 findings 一并复制进台账尾部**。回归轮从台账尾读回该标识——**台账本身就是凭据的存储**。
- **何时可新建**：**仅当**确证其一——① 运行时**无法**续接；② 原上下文不可用（进程消失 / 损坏）。**「不确定能不能」不等于「不能」**——先试续接，失败才落新建。
- **标注**：走新建时，在「评审记录」的「独立性」字段写 `<新建：续接失败>` 或 `<新建：运行时无续接能力>`，**并附一句证据**。**无证据的新建按违规计**。
- **禁止表述**：禁止把「每轮全新独立 subagent」写成合规做法，或把新建描述为「更符合独立性」——续接**不**破坏独立性（原 reviewer 从未参与修复）。

> **一致性提示**：「每轮换新上下文」与「核销后换上下文做终审」是两回事。前者一律不必要；后者**只在需要终审、且原上下文已核销过**时才必要——纯审多轮（从未核销）可全程复用一个上下文。

## 五、台账、职责面与分类

### 5.1 reviewer 角色与 prompt 模板

- **reviewer 输入**：artifact_path + criteria + 约束注入 + 职责面 + 完整台账 +（回归/终审轮）修复 diff + 受影响区域。
- **reviewer 输出**：findings-only，字段 `id / severity / desc / area / evidence / scope(in|out) / status`；**禁止复述工件、禁止长篇肯定**；结论为 通过 / 不通过 / BLOCKED（BLOCKED = 无法评审，如工件不可读、关键上下文缺失，须说明原因）。
- **reviewer 约束**：按下方「标定」客观赋值严重度，不主观预判 / 夸大；只审不改；可基于具体怀疑扩大读取并说明理由。

**标定**

| 档 | 含义 |
|---|---|
| Critical | 必须修复：功能性 / 内容性错误、安全问题、违反权限 / 文档红线 |
| Important | 应该修复：不正确的实现、遗漏的需求、维护性损害 |
| Minor | 锦上添花：命名优化、风格改进 |

**Read [prompts/reviewer.md](prompts/reviewer.md) now** and use it as the template for constructing each reviewer's prompt.

### 5.2 职责面与三档分类

对每一轮 findings（规则相同）：

| 档 | 判定 | 处置 |
|---|---|---|
| **必修** | 职责面内的 Critical/Important；或涉及安全 / 数据损坏 / 不可逆类（**无论落在哪里**） | 主 agent 修复 → 回归核销 |
| **路由** | 职责面外但真实存在的问题 | 记入「评审记录」的「后续事项」段（由调用方决定后续处置与落盘位置），**不阻塞**本次通过 |
| **驳回** | 偏好 / 风格 / 范围蔓延 | 记 Minor 或驳回，附理由，**不阻塞** |

**归属判定分工**：reviewer 发现问题并给出 scope 建议（in/out + 依据 + 证据）；主 agent 核定归属与处置。

**硬约束（防「生产者消音」）**

1. 主 agent **不得删除** reviewer 标为 in-scope 的 Critical/Important——只能改判，且**必须写明理由**；
2. 所有改判**记入台账**（可审计）；**分歧时默认按 in-scope 处理**；
3. 终审 reviewer 获得完整台账（含全部改判记录），**可对任何改判提出异议（reopen）**。

### 5.3 台账与轮数计数

**条目格式**：`id / severity / desc / area / evidence / scope / status`
（status ∈ open / closed / reopened；round_raised / round_closed 由主 agent 回填。reviewer 标识记于台账尾部。）

**轮数计数**：`max_rounds` 计**整个循环的评审轮总数**（首轮 + 回归 + 终审）。

- 一轮 = 一次完整的「评审输入 → 评审结论」周期；超大杯首轮并行 N 个 reviewer 仍计 **1** 轮；**修复动作不计轮**。
- 示例：首轮即 PASS = 1 轮；首轮 → 修 → 回归 clean → 终审 PASS = 3 轮。
- 走新建例外路径时：首轮 → 修 → 回归（新建 subagent，核销）→ 终审（新增一轮）= **4 轮**。
- 评审记录中分类标注：首轮 X / 回归 Y / 终审 Z。

## 六、档位与停止条件

### 6.1 深度档位

| 档位 | 形态 |
|---|---|
| **中杯**（默认） | 首轮 →（按需）修复 / 回归 →（发生过修复时）终审 |
| **大杯** | 完整台账 + 多轮回归 + 终审；其余规则相同 |
| **超大杯** | 首轮**并行** dispatch N 个独立 reviewer（各自独立上下文，N 显式声明、建议 3）合并 findings；「连续 2 轮无新增 Critical/Important」判稳定的既有规则保留；其余同大杯 |

> **附随改动豁免**：满足豁免（无可评审内容的附带改动）时可无需调用本引擎；但**交付物本身**为文档 / 配置等时**不得豁免**，一律默认中杯。

### 6.2 停止与暂停条件

| 条件 | 行为 |
|------|------|
| 职责面内无未关闭的 Critical/Important，且本轮无新增 | **进入终审**（若全程未发生修复 → 直接结束） |
| 达到 `max_rounds`（默认 6）仍未终审通过 | **停止循环。6 是停止信号，不是「再来一轮」的信号。** 输出未收敛报告（未决项 + 建议）并**直接呈现给用户**（不得只写入 plan.md 后静默继续）；由用户决定是否重入 |
| reviewer 连续返回 BLOCKED | 暂停，报告具体阻塞原因 |
| 工件与其依据基线（调用方提供的上游文档 / 标准）冲突 | 暂停，报告矛盾点，**不自行裁决** |
| 依据基线与实际实现矛盾 | 暂停，报告矛盾点，**不自行裁决** |

## 七、评审记录（留痕格式）

写入调用方指定的位置；独立调用时直接输出：

```
## 评审记录
- 工件：<名称或路径列表>
- 独立性：完整 / 受限 / 新建（新建 = 回归轮未续接原 reviewer，须附理由与证据，见 §4.5）
- 档位：大杯
- 轮数：首轮 1 / 回归 2 / 终审 1（合计 4）
- 核销人：<做过核销的 reviewer 标识清单>（终审资格判据，见 §1）
- 问题清单：
  - R1-CRIT-01 边界未处理 → closed in R2（核销人：R）
  - R1-IMP-02 命名不规范 → closed in R2（核销人：R）
  - R3-MIN-05 注释冗余 → closed in R3（核销人：R）
- 结果：PASS
```

## 八、常见陷阱（Gotchas）

- **不得删除** reviewer 标为 in-scope 的 Critical/Important——只能改判并写明理由。
- **不得以成本为由**裁剪 reviewer 输入或限制其读取；读取自主权见 `prompts/reviewer.md`。
- **6 是停止信号**，不是「再来一轮」；到顶未收敛就输出未收敛报告并交用户，不引入「升级给人」之外的步骤。
- **不要把「新眼睛」读成「每轮开新 subagent」**：硬约束只要求「核销者不得自证」，不要求「每轮新进程」。
- **不要只盯"最后一轮有没有核销"**：核销是**上下文**属性——同一个 reviewer 若在第 2 轮核销过，第 3 轮即使没核销，也**不能**担任终审（等于跨轮自证）。看的是"哪个上下文核销过"，不是"最后一轮做了什么"。
- **不要替调用方制定策略**：引擎只执行传入的 `depth` / `max_rounds` / `criteria`；仅独立调用时做轻量推断。
- **谁修**：修恒由主 agent 在循环内执行，reviewer 只审不改；不 dispatch 独立 fixer subagent。
- **超大杯并行 reviewer** 各自独立上下文，互不看到对方 findings；由引擎合并去重。

## 九、联动设计

- **集成方式**：由调用方文档规定；本引擎不感知调用方与其上游体系。
- **完成后输出**：`评审记录`（PASS / 未收敛）→ 由调用方写入其指定位置。
- **拒绝路径**：参数缺失或 artifact 类型无法判断时（独立调用），向用户确认一次，不反复追问。
