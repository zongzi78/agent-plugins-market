# sdd-apply（执行实施）

## 定位

按 plan.md 实施变更：

1. 分析任务依赖，判定串行 / 并行执行顺序
2. 调度 implementer subagent 执行独立任务，并把产物评审**委托**给 `sdd-review`
3. 通过评审引擎的循环（引擎内部定义）保障交付质量
4. 输出结构化变更摘要供 sdd-sync 消费

**主链路**：实现（步骤 3）→ **验证**（步骤 4）→ **评审**（步骤 5）→ 摘要（步骤 6）。

> 次序不可颠倒：**评审必须站在已验证的产物上**——先跑通编译 / 测试，再送审；否则 reviewer 审的是可能根本跑不起来的东西，白费轮次。

## ⚠️ 铁律

**只修改项目产物（代码 / 文档 / 配置等），绝不修改 `.ai/doc/` 下的任何文件。**

文档变更是 /sdd-sync 的专属职责。apply 阶段按需读取相关 `.ai/doc/` 章节（不预加载全文），仅用于上下文参考。实现中发现文档需要变更 → 记录到 plan.md 的「文档变更」表，由 sync 处理。

## 一、前置检查（Hard Gate）

1. **无活跃 change** → 拒绝："请先通过 /sdd-propose 创建 change"。
2. **plan.md 状态检查**：
   - plan.md 为空（仅占位 front matter）→ 拒绝："请先通过 /sdd-explore 制定实施方案"。
   - 读取 proposal.md 与 plan.md 的 `status`；proposal.md 缺失 → ⚠️ 警告"change 目录异常"，终止并提示检查 /sdd-propose 是否完整创建。
   - 两者不一致 → ⚠️ 警告"proposal 与 plan 的 status 不一致，可能存在状态管理错误"，并**一律视为未获批准**（不因任一为 approved 而放行）。
   - 不一致 或 均 ≠ `approved` → ⚠️ 警告 + AskUserQuestion：
     | 选项 | 含义 |
     |---|---|
     | 1（推荐，默认光标） | **回 explore 确认方案** —— 取消本次 apply，用户确认后重新执行 |
     | 2 | **强制执行（绕过审批）** —— 用户确认方案无误并显式授权；执行前将 proposal / plan 的 status 同步为 `approved` 并留痕 |
     | 3 | **取消** |
3. **多个活跃 change** → AskUserQuestion 让用户选择。
4. **断点续传**：plan.md 有 `- [x]` → 提示"检测到部分任务已完成（X/N），将从第一个未完成任务继续"。
5. **VCS 上下文**：优先读 `.ai/project-log.md`「VCS 状态」；缺失时现场探测（向上逐级查 `.git`/`.svn` 至文件系统根、向下查嵌套仓库目录（深度 ≤ 3 层））。
   - "有 git 仓库" = 目录树存在 `.git` 含向上继承，**非**"安装了 git 命令"。
   - 若为 git 仓库且当前在 main / master 分支 → 简短提醒"⚠️ 当前在 main 分支，建议确认是否需要创建功能分支"，**不阻塞**。
   - 无 git 时无此提醒。

## 二、改前留痕（见 supplement-rules §6）

在无 git 的项目中，本技能执行前必须先做两件事：

1. **就绪性检查**：运行 `change-backup selfcheck` 确认机制可用；**不可用 → 停止执行**。
2. **起始基线**：对本次 apply 计划**修改或删除的既有文件**做 `change-backup snapshot`。

此后每次修改 / 删除既有文件前的留痕、绑定值、失败处理，一律按 `.ai/supplement-rules.md` §6 执行（本技能不再重复）。

## 三、执行流程

### 步骤 1：加载与核对（就绪性检查，非质量评审）

1. 读取 `.ai/supplement-rules.md`（如存在）：
   - §一（权限边界）→ 确认 implementer 决策范围
   - §二（强制暂停规则）→ 实现中遇歧义时对照
   - §四（文档操作红线）→ 评审时的约束依据
   - 项目特定约束节 → 分类提取：
     - 所有 **ENV 约束**（启用=是）→ 注入 implementer 的 prompt
     - 所有 **CI/AC/DP 约束**（启用=是）→ 随评审调用注入（见步骤 5）
2. 读取 plan.md、proposal.md、相关 `.ai/doc/` 文件（含 `04-问题与改进.md`，确认已知陷阱）。
3. 逐项检查：
   - [ ] plan.md 中每个文件路径存在，或有创建步骤
   - [ ] 每个任务有验证步骤 + 预期输出
   - [ ] 任务引用的依赖都已定义
   - [ ] 任务顺序尊重数据依赖
   - [ ] plan.md 覆盖 proposal.md 的全部范围
   - [ ] `## 文档变更` 章节的每个目标文件路径正确
   - [ ] **文档操作红线**：确认所读 `.ai/doc/` 内容仅用于上下文参考；任何情况下不修改这些文件
4. **冲突预扫描**：
   - [ ] 是否有任务操作同一文件的同一区域（冲突风险）
   - [ ] 是否有任务间的隐式依赖未被 plan.md 标注
   - [ ] plan.md 的全局约束是否与任务描述矛盾
   - 发现问题 → **一次性列出**向人类确认，**不可自行裁决或假设"应该是这样"**。
5. 如有疑虑：向人类提出，不猜测。

### 步骤 2：并行度分析与编排

1. 对每个任务分析：

   **可并行**（须满足全部）：
   - 操作的文件集合与其他并行任务不重叠
   - 不依赖其他任务的输出或副作用
   - 不修改其他任务需读取的共享模块接口

   **必须串行**（满足任一）：
   - 同一文件被多个任务修改
   - 任务 B 依赖任务 A 的产出（类型定义、函数签名、数据结构）
   - 任务 B 需在任务 A 建立的模式 / 框架下工作
   - 基础设施任务（如"搭建项目结构"）须在其他任务之前

2. 输出编排方案（写入 plan.md 或进度记录）：
   ```
   批次 1：Task A ∥ Task B（并行，操作不同文件，无依赖）
   批次 2：Task C（串行，依赖 A 的接口定义）
   批次 3：Task D ∥ Task E（并行，共享 C 的产出）
   ```
3. 特殊情况：
   - 所有任务必须串行 → 按 plan.md 原始顺序执行，**不启动 subagent**
   - 只有一个任务 → 直接执行，**不启动 subagent**
   - 无并行编排 → 跳过编排自查
4. 有并行编排时，对**编排方案**做一次自查（仅编排合理性，非产物评审）：检查并行任务是否确实操作不重叠的文件集；检查串行排序是否尊重隐式依赖。发现风险 → 调整后执行。

### 步骤 3：逐批次执行（实现）

1. 创建 TodoWrite（内容来自 plan.md 任务清单）。
2. 对每个批次：

   **【串行批次 — 主 agent 直接执行】**
   - 标记 in_progress → 严格按 plan 步骤执行 → 运行验证
   - 为修改的产物补充规范说明（设计意图、边界条件），**禁止写入文档路径引用**
   - 同步更新 plan.md checkbox（`- [ ]` → `- [x]`）

   **【并行批次 — subagent 执行】**
   - **Read [prompts/implementer.md](prompts/implementer.md) now** and use it as the template for constructing each implementer's prompt.
   - 为批次内每个任务**并行** dispatch implementer subagent，填入：
     · 该任务的 plan.md 原文（精确步骤 + 验收标准）
     · 任务上下文（1-2 句，该任务在整个 change 中的位置）
     · 相关的 `.ai/doc/` 规范摘要
     · plan.md 的全局约束（命名规范、技术栈限制等）
   - **禁止**在 prompt 中粘贴：会话历史、之前任务的执行摘要、无关内容
   - 所有 implementer 完成后 → 标记该批次所有任务 completed 并同步 plan.md checkbox

   > 本步骤**不做**任务级评审；产物评审统一在步骤 5（见「为什么不在每任务后评审」）。
3. 遵循 plan 中的 commit 节奏。

### 步骤 4：验证（产出证据）

1. 运行与产物相关的验证（测试 / 构建 / 文档校验，按产物类型选择）→ 确认通过。
2. 回顾 plan.md，确认所有 checkbox 已勾选。
3. **铁律：没有验证证据不得声称完成。** 若工作空间不具备运行验证的条件，应**核对** plan.md 与对应修改，确认每个任务都已执行。
   > 这是**任务完成度核验**，**非**质量评审——产物评审是步骤 5 的独立环节。
4. 每个验证结论**附带具体证据**（符号锚点 / 测试输出行 / diff 片段 / 文档章节），**不依赖主观判断词**。

### 步骤 5：变更产物评审（质量闸门）

本 change 存在**任何产物变更**（代码 / 文档 / 配置）时，在此完成产物评审。

**闸门约束** —— 在取得「评审记录」之前，**不得**：

- 调用 `/sdd-sync` 或 `/sdd-archive`；
- 在 plan.md 标记 `status: completed`。

> 汇报进度**不受限制**——上述限制只针对这两个动作。

**调用**

```
sdd-review(artifact=产物类, criteria=产物评审标准, depth=声明/默认中杯,
           artifact_path=<变更文件/产物列表>, workdir=项目根,
           diff 基线=本次实现 diff, context=约束注入)
```

> **不内联全文**：只传路径 + criteria + 约束注入 + diff 基线；reviewer 自行按需读取工件。
> 约束注入由本 agent 传入（来源：步骤 1 已读取的项目规则）。

apply 只负责**提供** `criteria` 与约束注入、并**消费**「评审记录」结果。评审循环（reviewer 调度、台账、多轮回归、终审）由引擎内部处理；修复由主 agent 在循环内执行，apply 不介入。

> **反自审条款**：「行为自查」「自我审查」「自查表」「逐条对照 plan 检查」**均不构成评审**——这些属 implementer 职责（见 `prompts/implementer.md`「自我审查」），发生在步骤 3 内。本步骤的评审**只能**由 sdd-review 引擎派发的独立 reviewer 产出。**主 agent 自审 = 未评审。**

**产物评审标准（apply 提供，作为 `criteria`）**

1. **spec 合规**：是否完整实现 plan 中该任务全部要求。
2. **质量**：逻辑 / 内容正确、边界条件、符合项目规范；代码类产物检查无 YAGNI，文档 / 配置类产物检查内容准确性与必要性。
3. **约束合规**：是否违反 `.ai/supplement-rules.md` §一 / §四 及 ENV / CI / AC / DP 约束。
4. **红线**：绝不越权修改 `.ai/doc/`（若发现需要改 → 记录到 plan.md 的「文档变更」，交 sync）。

**评审结果处理**

| 结果 | 处理 |
|------|------|
| PASS | 任务完成，可标记 `completed` |
| Minor 问题 | 记录到 plan.md 该任务备注，**不阻塞** |
| 未收敛（达到轮数上限或发现矛盾） | 停止循环，输出未收敛报告（未决项 + 建议） |

**豁免与档位**

- **附随改动豁免**：满足豁免（无可评审内容的附带改动）时可无需调用评审；但**交付物本身**为文档 / 配置等时**不得豁免**，一律默认中杯。
  > **不可误用**：豁免仅限无语义的附随改动（纯注释 / 空行 / 格式 / 非交付性说明）；涉及可执行逻辑或作为交付内容时一律按默认中杯走评审，**不可用行数或文件数做依据**。
- **单向严格**：评审深度只能向上（大杯 / 超大杯），**不得降级或跳过**；要降级须显式询问人类。
  > 已取消原「按大小跳过」逻辑（<10 行 / 单文件 / 特定类型），只保留上述豁免。

### 步骤 6：输出结构化变更摘要

1. 确认 plan.md 全部 checkbox 已勾选，且步骤 5 已产出「评审记录」。
2. 将「评审记录」（含档位 / 轮数 / 问题清单 / 结果）追加到 plan.md 末尾。
3. 输出以下摘要（供 sdd-sync 与 sdd-archive 使用）：

```
## 变更摘要（apply 生成）

改动的符号 / 条目:
  - 修改: ClassName::methodName() — 简要描述变更
  - 新增: ClassName::newMethod()
  - 删除: ClassName::removedMethod()
  - 修改: docs/guide.md §运行说明 — 行为描述变更（文档产物示例；`.ai/doc` 变更由 sdd-sync 处理）
  - 新增文件: path/to/new/file
  - 删除文件: path/to/removed/file
```

> 代码产物用符号锚点；文档 / 配置产物用文件路径 + 章节 / 条目。

4. 追加此摘要到 plan.md 末尾。
5. **交叉检查实际变更**：有 git 用 `git diff`；无 git 用快照 diff（`.ai/backups/`）——确认摘要覆盖全部实际变更；发现遗漏 → 补充进摘要并标注 `⚠️ apply 摘要遗漏`。

## 四、Subagent 调度规范

### 角色

apply 只调度**实现者**（implementer）。评审（reviewer 调度、循环、台账、多轮回归）由评审引擎内部处理；修复由主 agent 在循环内执行 —— 均不在 apply 描述范围。

| 角色 | 职责 | 输入 | 产出 |
|------|------|------|------|
| implementer | 按 plan 步骤实现产物 | 任务原文 + 相关文件路径 + 全局约束 | 产物变更 + 自验证结果 |

**模型选择**：implementer 使用当前会话模型；任务涉及复杂架构判断时，考虑使用更强模型。

### Implementer 状态处理

| 状态 | 处理方式 |
|------|---------|
| 完成 | 进入后续步骤 |
| 完成但有疑虑 | 先读 concerns：涉及正确性 / 范围则处理后再继续；仅是观察则记录并继续 |
| 需要更多上下文 | 补充信息，重新 dispatch |
| BLOCKED | 1) 补充上下文重试 2) 拆小任务 3) 报告人类 |

> **BLOCKED 语义**（两侧一致）：implementer 的 BLOCKED = 无法实现 / 无法推进（如遇阻碍、缺少必要条件），须说明原因并列出已尝试项；reviewer 的 BLOCKED = 无法评审。两者均为「**无法继续、须说明原因**」。

## 五、执行原则

- **连续执行**：不在任务间询问"是否继续"。人类调用 sdd-apply = 授权执行全部任务；只在遇到阻塞、歧义、或全部完成时暂停。
- **最小旁白**：任务间不输出进度摘要或反思——TodoWrite 与 plan.md checkbox 已记录状态。
- **冲突即停**：发现 plan 描述与产物现实矛盾时，**不自行裁决**，立即报告。
- **禁止并行操作同一文件**：即使编排方案标为并行，若两任务操作同一文件的不同区域，**降级为串行**。
- **绝不碰 `.ai/doc/`**：即使发现明显笔误或过时信息，也不在 apply 阶段修改；记录到 plan.md → 由 sync 处理。apply 修改文档 = 数据不一致。

## 六、常见陷阱（Gotchas）

- **并行任务共享隐式约定**：implementer 只看到自己的任务 prompt。若两个并行任务共享隐式约定（如相同的工具函数签名），可能做出冲突决策 → 编排时优先将可能共享约定的任务**串行化**。
- **subagent prompt 膨胀**：容易为了给 implementer "更多上下文"而粘贴会话历史 → token 爆炸。严格遵循模板：只传任务原文 + 1-2 句上下文 + 全局约束。
- **变更摘要遗漏**：implementer 可能在实现 task A 时"顺便修了" task B 范围的小问题 → 步骤 6 必须交叉检查实际变更（git diff 或快照 diff），遗漏项补进摘要并标注。
- **附随改动豁免不可误用**（详见步骤 5）。

## 七、暂停条件

| # | 触发 | 行为 |
|---|---|---|
| 1 | 任务描述不清 | 询问，**不猜测** |
| 2 | 发现设计问题 | 暂停，建议更新 plan.md 或回退 sdd-explore |
| 3 | 遇到错误 / 阻塞 | 报告，等待指导 |
| 4 | 用户中断 | — |
| 5 | 连续验证失败 3 次 | 停止，**质疑方案本身** |
| 6 | 发现产物中已存在与 plan.md 矛盾的设计 | 暂停，报告具体矛盾点 |
| 7 | 评审未收敛（达轮数上限或发现矛盾） | 停止，输出未收敛报告（未决项 + 建议） |
| 8 | subagent 连续返回 BLOCKED | 暂停，报告具体阻塞原因 |

## 八、联动设计

- **拒绝路径**：见「一、前置检查」。
- **完成后引导**：`✅ 所有任务已完成（N/N），产出评审已通过（结果：PASS）。接下来可通过 /sdd-sync 将设计变更同步到项目文档（sync 将分析 apply 生成的变更摘要），然后通过 /sdd-archive 归档本次 change。`
- **暂停时提示**：`⏸ 实施暂停（M/N 任务完成）。问题解决后可再次运行 /sdd-apply 继续（支持断点续传）。`
